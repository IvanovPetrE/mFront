# Messenger — фронтенд (React + TS + Vite)

## Запуск

```bash
npm install
npm run dev
```

Бэкенд должен слушать `http://localhost:8000` (прокси настроен в `vite.config.ts`,
т.к. refresh-cookie строгая по `SameSite` и должна видеть один origin с фронтом).
Для другого адреса поменяй `server.proxy` в `vite.config.ts` либо задай
`VITE_API_BASE_URL` и `VITE_WS_BASE_URL` в `.env` и убери прокси — тогда бэкенд
должен сам прислать корректные CORS-заголовки с `credentials: true`.

## Как устроена авторизация во фронте

Повторяет схему из `auth.py`:

1. При загрузке фронт запрашивает `GET /auth/config`, затем сразу пытается
   `POST /auth/refresh` (с CSRF-заголовком из читаемой cookie) — если refresh-cookie
   жива, получает access-токен и остаётся в памяти вкладки (`tokenStore.ts`),
   **не** в localStorage.
2. Если refresh не удался — показывается экран логина, кнопка делает
   `window.location.href = /auth/login?next=...` (обычный редирект, не fetch:
   это часть OIDC-флоу с Keycloak).
3. `/auth/callback` полностью обрабатывает бэкенд и сам редиректит обратно —
   отдельного React-роута для callback не нужно.
4. Access-токен кладётся в `Authorization: Bearer` на все REST-запросы
   (`api/http.ts`). На 401 — один раз тихий `refresh` и повтор запроса.
5. Токен также обновляется по таймеру (за 30 сек до истечения `expires_in`).
6. WebSocket передаёт токен как `?token=` (по-другому в браузере нельзя —
   это и в комментарии `ws.py` отмечено). При закрытии с кодом `4401`
   (см. watchdog по `expires_at` в `ws.py`) фронт обновляет токен и
   переподключается, а не долбит тем же токеном.

## Два WebSocket-соединения, а не одно

- `/ws/chat/{id}` (`ws/useChatSocket.ts`) — открыт, только пока открыт
  конкретный чат. Несёт содержимое: сообщения, правки, удаления, статусы,
  typing.
- `/ws/me` (`ws/useMyEventsSocket.ts`) — держится всю сессию, не привязан
  к чату. Несёт только `{"event": "chat.updated", "data": {"chat_id"}}` —
  сигнал "перечитай список чатов", без текста сообщений. Без него
  сообщение в свёрнутом чате не обновило бы бейдж непрочитанных и превью
  в `ChatList.tsx`, пока не откроешь его вручную или не перезагрузишь
  страницу — у `/ws/chat/{id}` физически нет доступа к чужим комнатам.

Это требует изменений на бэке — они не в этом архиве, отдельно, в
`backend-changes.zip`: новый обработчик `/ws/me` в `ws.py` и
`notify_chat_updated` в `services.py`/`chats.py`/`messages.py`. Без
применения бэкенд-патча `/ws/me` ответит 404, и `useMyEventsSocket` будет
уходить в бесконечный реконнект — не страшно (просто лишние попытки раз в
15 секунд), но список чатов не будет обновляться сам собой, пока патч не
накатят.

## Допущения, которые стоит перепроверить

Типы (`src/api/types.ts`) сверены с `schemas.py`, `models.py` и
`websocket.py`, `services.py`. Все файлы бэкенда теперь просмотрены,
контракт подтверждён кодом, а не догадками:

- `message.created` / `message.updated` — `{ event, data: <MessageOut> }`,
  собирает `broadcast_message` в `services.py`.
- `message.deleted` — `{ event, data: { id, seq } }`, собран вручную в
  `messages.py`.
- `message_status` — **отдельное** событие (не `message.updated`!),
  `{ event: "message_status", data: { message_id, status } }`, его шлёт
  `update_message_status` в `services.py`.
- `typing` — `{ event: "typing", data: { user_id, username, is_typing } }`.

REST-эндпоинт `POST /messages/{id}/status` в `messages.py` объявлен дважды
с одинаковым путём — рабочий (первый по порядку регистрации в FastAPI)
принимает `status` как **query-параметр**, не JSON-тело; второй
обработчик (с телом `{delivery_status}`) недостижим. Первая версия фронта
была написана под мёртвый обработчик — уже поправлено в `messages.ts`
(`?status=...`, без тела). На бэке дублирующий хендлер стоит всё равно
удалить, чтобы не путать следующего человека.

Также добавлена автоматическая простановка `read`: при открытии чата
(`ChatWindow.tsx`) фронт теперь сам зовёт `/status?status=read` для
входящих сообщений (только не для своих — иначе бэкенд ответит 403).

При восстановлении WebSocket-соединения после разрыва (`onReconnected` в
`useChatSocket.ts`) фронт перезапрашивает последнюю страницу сообщений
целиком — Redis pub/sub ничего не буферизует, и события, случившиеся
во время разрыва, теряются безвозвратно. У бэкенда нет параметра
"дай сообщения после seq X" (`before_seq` — только назад), поэтому
честного докачивания дельты нет; полный рефетч страницы — единственный
способ гарантированно не разойтись с сервером в рамках текущего API.

`deps.py` подтвердил: REST ждёт `Authorization: Bearer <access-токен>`
через `HTTPBearer` — именно так и делает `api/http.ts`.

### Важно при локальном запуске

Бэкендовский README подчёркивает: `redirect_uri` Keycloak сверяет
побайтово, а `localhost` и `127.0.0.1` для OAuth — разные адреса. Раз
`PUBLIC_BASE_URL` по умолчанию `http://localhost:8000`, открывать наш
dev-сервер нужно строго по **`http://localhost:5173`** (не `127.0.0.1:5173`),
иначе `/auth/login` уйдёт на Keycloak, а `/auth/callback` на бэке даже не
попытается сверить `redirect_uri` — до него не дойдёт, но cookie состояния
входа (`mg_txn`, `SameSite=Lax`) просто не долетит обратно при таком
рассинхроне хоста.

### Режим `AUTH_DISABLED=true`

В `deps.py` в этом режиме `get_current_user` вообще не проверяет заголовок
и всегда отдаёт одного dev-пользователя — REST работал бы и без токена. Но
`POST /auth/refresh` в `auth.py` по-прежнему требует refresh-cookie, а
`GET /auth/login` в этом режиме её не ставит (сразу редиректит на `next`).
Итог: наш фронт в `AUTH_DISABLED=true` зависнет на экране логина — `refresh`
всегда будет отвечать 401, хотя бэкенд к запросам без токена уже готов.
Для этого режима фронту нужен отдельный обход (например, не дёргать
`/auth/refresh` и не требовать токен, если `auth_disabled: true` пришёл из
`/auth/config`) — сейчас в коде этого нет, добавь при необходимости.

## Аудит безопасности

### Что уже сильно сделано на бэке (не менялось, просто зафиксировано)

- Authorization Code + PKCE, `state`/`nonce`, обмен кода на токены — только
  на сервере (`auth.py`, `oidc.py`).
- Refresh-токен — `HttpOnly` + `Secure`(в проде) + `SameSite=Strict`,
  область действия сужена до `path=/auth`.
- Double-submit CSRF (`mg_csrf` + заголовок `X-CSRF-Token`) — вторая линия
  защиты на случай браузера, который не соблюдает `SameSite`.
- `safe_next_url` рвёт open redirect через `?next=`.
- `security.py`: allowlist алгоритмов подписи JWT (без этого возможна
  классическая атака `"alg": "none"`), проверка `iss`/`aud`/`exp`.
- REST-эндпоинты чатов/сообщений используют `Authorization: Bearer`, а не
  cookie — это само по себе защищает их от CSRF (подделать заголовок
  из чужого сайта browser-формой нельзя).

### Что было дырой во фронте и теперь исправлено

1. **Истечение сессии посреди работы не приводило к экрану логина.**
   `tokenStore.subscribe(...)` был написан заранее, но не использовался.
   Теперь `AuthContext.tsx` подписан на него: как только токен где угодно
   обнуляется (неудачный silent-refresh по таймеру, 401→refresh в
   `api/http.ts`, код `4401` у WebSocket) — статус переключается на
   `anonymous`, и `RequireAuth` показывает экран логина вместо тихо
   умирающего интерфейса.
2. **`logout()` не переживал сетевой сбой.** Если `POST /auth/logout`
   падал не HTTP-ошибкой, а сетевым исключением, оно нигде не ловилось:
   локальный токен не чистился, редиректа не было — пользователь нажимал
   «выйти» и оставался залогинен. Теперь запрос обёрнут в `try/catch`,
   `tokenStore.set(null)` вызывается безусловно, и при недоступном
   бэкенде фронт просто уходит на `/` вместо адреса выхода Keycloak
   (`end_session_url` в этом случае построить не из чего).

### Доработки по итогам сравнения с альтернативной реализацией (ChatGPT-фронтенд)

Сравнили наш фронтенд с независимой реализацией того же бэкенда (React 19 +
TanStack Query + axios). Архитектурно она сложнее (кэш React Query,
generation-счётчики в realtime-провайдере), но три её конкретных решения
были объективно сильнее наших и перенесены сюда:

1. **Дедупликация конкурентного `refresh()`.** `tokenStore.refresh()`
   раньше не проверял, не идёт ли уже обновление токена: если 401
   прилетал одновременно на несколько параллельных запросов (например,
   список чатов и список пользователей грузятся вместе при старте),
   каждый инициировал свой `POST /auth/refresh`. Теперь все конкурентные
   вызовы разделяют один и тот же in-flight `Promise` — на бэкенд уходит
   один запрос вместо N.
2. **Ранжирование `delivery_status` при WS-обновлении.** `message_status`
   по WebSocket мог прийти с опозданием или не по порядку — Redis
   pub/sub и переподключение это не гарантируют. Раньше обработчик
   просто перезаписывал статус тем, что пришло, поэтому устаревшее
   `sent`, доставленное позже `read` (например, после реконнекта),
   откатывало бы статус в UI назад. Теперь статус меняется только вперёд,
   по шкале `sent(0) < delivered(1) < read(2)` (`ChatWindow.tsx`,
   `STATUS_RANK`).
3. **Таймаут индикатора «печатает…».** Если у собеседника обрывалась
   связь или закрывалась вкладка ровно во время набора текста, событие
   `is_typing: false` могло не дойти вовсе — индикатор оставался
   показанным навсегда. Теперь на каждого печатающего пользователя
   заводится таймер на 4 секунды (заметно больше 1.5-секундного debounce
   в `MessageInput.tsx`), который сам гасит индикатор, если следующее
   событие не пришло.

### Остаточные риски — не код фронта, а вопрос деплоя

- **Access-токен в URL WebSocket** (`?token=...`) — иначе браузер не умеет
  передать заголовок на handshake. Токен живёт 5 минут, но если это
  когда-нибудь окажется за nginx/другим reverse proxy, стандартный лог
  доступа пишет полную строку запроса вместе с query string — токен
  осядет в логах. При деплое стоит явно выключить логирование query
  string для пути `/ws/` (для nginx — `log_format` без `$request` целиком,
  или маска).
- **XSS остаётся в целом теоретическим, но не нулевым риском для
  access-токена.** Сам контент сообщений безопасен (React экранирует
  `{message.content}` при рендере, `dangerouslySetInnerHTML` в проекте не
  используется нигде — проверено). Но если XSS попадёт в проект через
  сторонний скрипт/зависимость, токен в памяти вкладки всё равно
  достижим тем же JS-контекстом, просто недоступен через
  `localStorage`/DOM напрямую. Это ограничивает, а не убирает
  риск — отсюда и короткий TTL access-токена на 5 минут в конфиге
  Keycloak, это осознанный компромисс, а не недосмотр.
- **CSP-заголовок** при сборке в `dist/` не задан — это задача сервера,
  который будет раздавать статику (nginx/Cloudflare/что угодно), не
  самого React-приложения. Инлайн-скриптов в сборке Vite нет, так что
  строгий CSP (`script-src 'self'`) встанет без переделок кода.

- `delivery_status` в модели — одно поле на сообщение, а не запись per-recipient
  (в отличие от `last_read_seq`, который per-member). В группе из трёх
  человек последний, кто откроет чат, перезапишет статус на `read` для
  всех — это ограничение бэкенда, не фронта.
